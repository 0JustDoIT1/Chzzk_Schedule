# 배포 전 프록시 IP 확인

백엔드는 기본적으로 TCP 접속 IP를 제보 요청량 제한의 기준으로 사용한다. `X-Forwarded-For` 요청 헤더는 기본 설정에서 무시한다.

프록시가 백엔드 앞에 있고 백엔드에 직접 접속할 수 없도록 차단한 경우에만 `TRUST_PROXY_HOPS`를 설정한다. 백엔드에서 바깥쪽으로 역추적해 신뢰할 프록시 수를 1~5의 정수로 지정한다. 예를 들어 프록시가 하나면 `TRUST_PROXY_HOPS=1`이다. 설정값이 없으면 직접 접속 IP를 사용하며, 범위를 벗어난 값은 시작 시 오류로 처리한다.

배포 후에는 서로 다른 외부 IP에서 제보 제한이 분리되는지, 같은 IP에서 시간당 10건 제한이 적용되는지 확인한다. 직접 백엔드 접속 경로가 남아 있다면 헤더 위조로 제한을 우회할 수 있으므로 프록시 전용 접근 제한을 먼저 적용한다.

공개 사이트 주소가 확정되면 프런트엔드 빌드 환경에 `SITE_URL=https://실제-공개-도메인`을 설정한다. 루트 메타데이터의 `metadataBase`가 이 주소를 사용하며 Open Graph 등의 상대 주소가 공개 도메인으로 해석된다. `SITE_URL`은 사이트 주소만 넣고 경로·쿼리는 넣지 않는다. 현재 로컬 빌드에는 배포 주소가 없어 이 변수를 설정하지 않는다. 테스트 도메인으로 빌드했을 때 이미지 메타 태그에는 그 도메인이 반영됐지만 Next.js 15.1.4의 빌드 경고는 계속 출력됐다.

## 배포 후 읽기 전용 점검

공개 사이트와 백엔드 점검 주소가 정해지면 `SITE_BASE_URL`, `API_BASE_URL`, `EXPECTED_METADATA_BASE`를 설정하고 저장소 루트에서 `node apps/front-end/scripts/verify-http-rendering.js`를 실행한다. 이 스크립트는 준비 상태, 첫 화면 이동, 오늘·월간 화면, 제보 확인 404와 비공개 응답 헤더, Open Graph 이미지의 공개 주소를 확인한다. 백엔드 점검 주소는 외부 공개가 필요하지 않으며 내부 실행 환경에서 접근할 수 있으면 된다.

배포 플랫폼에서 프록시 단계 수와 백엔드 직접 접속 차단을 확인한 뒤, 서로 다른 실제 외부 IP에서 제보 제한이 분리되는지 점검한다. 정상 접수 요청을 대량으로 만들지 말고 격리된 시험 환경에서 한도와 우회 여부를 검증한다. 오류 로그 수집 경로와 보존 설정을 확인하고, 운영 백업을 별도 격리 DB에 복원해 문서 수·인덱스·핵심 조회를 비교한다. 샘플 로컬 백업 복원은 운영 백업 검증을 대신하지 않는다.
